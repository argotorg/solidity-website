[Solidity v0.8.39](https://github.com/argotorg/solidity/releases/tag/v0.8.39) has been released.

This release fixes a medium-severity bug that could silently corrupt storage.
It occurred when a recursive struct in storage was copied over a storage struct that contained it.
The release also fixes a miscompilation of nested tuple assignments in the evmasm pipeline.
We do not consider that bug a security issue.

When compiling with `--evm-version amsterdam`, the compiler now warns about contract code larger than 64 KiB and initcode larger than 128 KiB.
[EIP-7954](https://eips.ethereum.org/EIPS/eip-7954) raises the [EIP-170](https://eips.ethereum.org/EIPS/eip-170) limit for contract code from 24 KiB to 64 KiB, and the [EIP-3860](https://eips.ethereum.org/EIPS/eip-3860) limit for initcode from 48 KiB to 128 KiB.
For all other EVM versions, including the current default Osaka, the warnings still use the old limits.
Support for the Amsterdam EVM version is still experimental.

The compiler now also warns about code size when it compiles standalone Yul code, as it already did for Solidity code.

This is likely the last release of the 0.8 series, and the next release will be 0.9.0.

## Important Bugfixes

### Overlapping Recursive Storage Struct Copy Corruption

A struct is recursive when it can contain values of its own type, as in `struct Node { Node[] children; uint256 data; }`.
The bug occurred when such a struct, or an array of such structs, was copied within storage to a location that contained it.
Examples are `root = root.children[0]` and `roots = roots[0].children`, with `root` of type `Node` and `roots` of type `Node[]` in storage.
The overlap is not always visible in the assignment, for example when the source is reached through a storage pointer, a mapping key or an array index.
Copying the array rewrote the storage area that held the source before the copy had finished reading it.
The elements nested in the source were lost, and the members declared after the array came back as zero.
No error was reported.
Both the evmasm and the IR pipeline are affected, independently of the optimizer settings and the EVM version.
Versions 0.4.9 through 0.8.38 are affected with the evmasm pipeline, and versions 0.8.13 through 0.8.38 with the IR pipeline.

The fix adds a runtime check to every storage-to-storage copy of a recursive struct or an array of such structs.
The check costs extra gas, even when the source and the target do not overlap.
The check also uses stack space while it walks the target.
Copies into deeply nested targets can therefore run out of stack space at a smaller depth than before, and fail.
In one example compiled with `--via-ir` and the optimizer, the maximum depth dropped from 252 to 126 levels.

We scanned the verified contracts in the [Sourcify](https://sourcify.dev/) database and found no deployed contract that performs an affected copy.

The bug was reported by [cyberthirst](https://x.com/cyberthirst) through the Ethereum Foundation's bug bounty program.

Write-up: [Overlapping Recursive Storage Struct Copy Corruption Bug](/blog/2026/11/19/overlapping-recursive-storage-struct-copy-corruption-bug/)

## Other Miscompilations

### Swapped Values in Nested Tuple Assignments

In the evmasm pipeline, a tuple assignment could assign values to the wrong variables.
This happened when a nested tuple on the right-hand side contained a string literal next to another value.
The literal also had to be assigned to a `bytes32`, `bytes` or `string` variable.
For example, with `bytes32 z` and `uint256 a`, the assignment `((z, a), b) = (("x", 111), 222)` assigned `111` to `z` and `bytes32("x")` to `a`.
No error or warning was reported.
The IR pipeline is not affected, and the optimizer settings do not matter.

We do not consider this a security issue, because the pattern is unusual and unlikely to be used in practice.
Nested tuples are mainly useful for capturing the results of function calls, and a function call cannot return a string literal.
Other than that, nesting offers no advantage over a flat tuple assignment or a series of simple assignments.
If the value of a string literal ends up in a memory or calldata reference, using that reference will likely cause an out-of-gas revert.
Testing should catch that.

## Notable Features and Changes

### `ethdebug` Type and Layout Information (Experimental)

With `--ethdebug-resources`, the compiler now emits the full [`info/resources` schema](https://ethdebug.github.io/format/spec/info/resources) of the ethdebug format.
This is how the compiler describes [types](https://ethdebug.github.io/format/docs/concepts/types/) and [their layout](https://ethdebug.github.io/format/docs/concepts/pointers/) to debuggers.
It is also a prerequisite for passing debug data through Yul.
ethdebug output remains experimental and requires `--experimental`.
For an introduction to the format, see [ethdebug: a shared language for debug data, in use across projects today](https://www.argot.org/blog/2026-10-ethdebug).

## Solidity 0.9.0

For years, we planned 0.9.0 as a large breaking release that would make the IR pipeline the default.
Because of that, many users expect 0.9.0 to break a lot of code.
Our plans have changed.
We still plan to make the IR pipeline the default, along with the [SSA CFG code generator](/blog/2026/04/29/solidity-0.8.35-release-announcement/#experimental-ssa-cfg-code-generator), but we no longer tie this to 0.9.0.
Waiting for it was holding back other breaking changes that we can make earlier.
From now on, we want to make breaking releases more often and make them smaller.
As a result, the version number alone will not show how much a breaking release changes.
More frequent breaking releases also let us remove old features that we have kept through the long 0.8 release cycle.
We will explain the new release schedule and the reasons for it in a separate post.

Most of the changes merged for 0.9.0 so far remove features that earlier 0.8 releases deprecated.
Examples are ABI coder v1, virtual modifiers, the `ABIEncoderV2` pragma, the SMTChecker's BMC engine and the EVM versions older than Constantinople.
We plan to publish a pre-release of 0.9.0 before the final release.

## Full Changelog

### Important Bugfixes

- Code Generator: Fix storage corruption when overwriting a recursive struct in storage with a struct nested inside it. Copying a recursive struct between storage locations now performs a runtime overlap check, taking a memory snapshot of the source when the target contains it.

### Compiler Features

- Commandline Interface: Omit the compilation record from `--ethdebug-resources` (experimental).
- ethdebug: Populate the type and pointer tables of `ethdebug/format/info/resources` with type documents and layout-specific pointer templates for storage, transient storage, memory and calldata (experimental).
- ethdebug: Stamp the `ethdebug/format/program` and `ethdebug/format/info/resources` outputs with their schema and the version of the ethdebug/format specification they follow (experimental).
- EVM: Warn about exceeding the increased contract code size (64 KiB) and initcode size (128 KiB) limits instead of the EIP-170 and EIP-3860 limits when compiling for the Amsterdam EVM version ([EIP-7954](https://eips.ethereum.org/EIPS/eip-7954)).
- Standard JSON Interface: Omit the compilation record from `ethdebug.resources` (experimental).
- Yul: Warn when the assembled bytecode of a compiled Yul object exceeds the EIP-170 (runtime code) or EIP-3860 (initcode) size limit, matching the existing warnings for Solidity input.

### Bugfixes

- Code Generator: Fix tuple assignments swapping values when a nested tuple component occupying at least one stack slot grows during type conversion.
- ethdebug: Fix incorrect source file IDs in instruction locations (experimental).
- SMTChecker: Fix empty tuples being printed as an undeclared constant in SMT-LIB queries, which made the solver reject every query of the affected contract.
- SMTChecker: Fix false negative in CHC engine when a function from abstract base is called externally using `this`.

## How to Install/Upgrade?

To upgrade to the new version of the Solidity Compiler, please follow the [installation instructions](https://docs.soliditylang.org/en/v0.8.39/installing-solidity.html) available in our documentation.
You can download the release from GitHub: [v0.8.39](https://github.com/argotorg/solidity/releases/tag/v0.8.39).

If you want to build from the source code, do not use the source archives generated automatically by GitHub.
Instead, use the [`solidity_0.8.39.tar.gz` source tarball](https://github.com/argotorg/solidity/releases/download/v0.8.39/solidity_0.8.39.tar.gz) or check out the `v0.8.39` tag via git.
